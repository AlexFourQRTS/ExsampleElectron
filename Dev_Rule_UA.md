# Правила розробки

**Опис:** Загальні правила стилю коду та принципи прийняття рішень  
**Автор:** Основна команда  
**Статус:** Завжди застосовувати  
---

## Мета правил

Людина не може утримати в голові більше 3–4 ланцюжків логічного розгалуження. Далі падає підтримка коду, зростає ризик багів при правках.

Усі правила цього файлу насамперед для **KISS**: код має читатися та змінюватися без «розпутування» логіки.

Обмеження (розгалуження, рядки у файлі, успадкування, utility-type, аргументи функції) — не бюрократія, а захист від перевантаження мозку.

Якщо два рішення рівні за завданням — вибирати простіше. Виняток: security / auth (правила безпеки важливіше за простоту).

---

## Коли правила суперечать одне одному

- **Мета правил (KISS, лімітування розгалужень)** — орієнтир при будь-якому виборі.
- **Критичні заборони** (any, interface, складні utility-type, security/auth без тестів) мають пріоритет над KISS — не послаблювати їх.
- **Новий код та рефакторинг** — за всіма правилами цього файлу.
- **Правка legacy без рефакторинга**: мінімальний diff та стиль сусідського коду; не додавати interface, any, default export; якщо в файлі існує else / interface, не торкатися його; новий код у тому ж файлі — без else та interface.
- **Не роздувати:** менше 50 рядків та одна задача = не розбивати на файли без причини.

---

## Мова та локалізація

- Весь новий код — **англійською**: вихідні файли, коментарі, повідомлення комітів, документація.
- Існуючий код іншою мовою: не торкатися без рефакторинга; при рефакторингу привести до правил.
- Без захардкоджених UI-рядків — окремий шар i18n (translations, locales тощо).
- Текти інтерфейсу, помилки та підписи — у перекладах, ключі англійською.

---

## Залежності

Перед реалізацією крупної задачі — перевірити, чи існує готовий перевірений модуль. Не писати своє для типових областей (Excel, PDF, crypto, HTTP-клієнт, розбір складних форматів тощо).

**Критерій «крупної»:** стандартний протокол/формат, криптографія, важкий розбір, OAuth, робота з файлами — шукати пакет. Бізнес-логіка проєкту — писати в репозиторії.

На дрібні утиліти (1–2 функції, вузька логіка проєкту) — не шукати пакет.

Після додавання: depcheck (невикористане), npm audit (CVE), репутація та активність пакета; в PR — 1–2 речення, чому вибран та які альтернативи розглядались.

Видаляти невикористані залежності з package.json.

## Архітектура та якість

- **Розмір файлу:** не більше 250 рядків. При перевищенні — розбивати на модулі. Legacy понад ліміт — split при наступному торканні.
- **Класи:** у одного базового класу — не більше 5 прямих спадкоємців; у класу — не більше одного базового (extends). implements — по мінімуму.
- **Більше 10 case за одним значенням:** Map або окремий файл стратегії, не switch на десятки гілок та не куча класів-спадкоємців.
- **SOLID, Clean Architecture, Strategy / Factory / Observer:** тільки якщо спрощують код, не заради моди.
- **Декларативний стиль:** без callback hell та глибокої вкладеності.
- **SRP:** у модуля, компонента або функції — одна зона відповідальності.
- **JSDoc для публічного API** (сервіси, стратегії, shared utils) — виняток з правила мінімуму коментарів.
- **Ім'я файлу = головний експорт;** один файл — одна публічна сутність.
- **Різні шари та точки входу** (UI, фон, API, CLI) — окремі файли, різна відповідальність.
- **Загальні type:** у окремому файлі при переиспользуванні в 2+ місцях або більше ~30 рядків.

## UI (оформлення)

- **Візуальне оформлення** через UI-бібліотеку, прийняту в проєкті (MUI, shadcn, Ant Design тощо): компоненти, тема, стилі.
- Не дублювати з нуля те, що бібліотека вже дає; не змішувати кілька UI-kit без причини.
- Оформлення відокремлено від бізнес-логіки.

## Безпека

- **Не комітити секрети, API-ключі, токени** — тільки env (.env, .env.local) та запис у .gitignore.
- **Критично:** security / auth — тести перед merge в main.

---

## Принципи реалізації

- **Мінімальний diff:** найменший коректний обсяг змін; не торкатися зайвого коду.
- **Без переусложнення:** жодних передчасних абстракцій, хелперів на один виклик та зайвої обробки нереальних кейсів.
- **Новий код та рефакторинг** — за цим файлом. **Правка legacy** — див. розділ «Коли правила суперечать».
- **Коментарі:** код зрозумілий сам по собі; коментарі тільки для неочевидної логіки, плюс JSDoc на публічний API.
- **DRY:** в runtime-коді та явних type; не через заборонені utility з розділу TypeScript.
- **KISS:** головна мета (див. «Мета правил»); **YAGNI** — не додавати те, без чого код і так зрозумілий.
- При рефакторингу старий код можна коментувати рядом; після merge — видалити, історія в git.

## Імена

- **Змінні та функції:** з двох слів; короткі імена тільки для локальних та загальноприйнятих (id, url, index).
- **Заборонені безликі:** handler, handle, process, data, temp — імя говорить, що робить.
- **camelCase** для JS/TS; в інших мовах — за прийнятими в мові правилами.

---

## Складність

**Головний ліміт:** завершена логічна гілка — не більше 4 позицій (if / switch / цикл / тернарник; && та || у рядку не рахуються). Це наслідок «Мети правил».

Один switch у функції = одна позиція, але case всередині — не більше 10 (інакше Map, див. Архітектуру).

- **Критично:** функція з більше 3 аргументами — один object-параметр.
- **else заборонений у новому коді** — ранній return; гілки завершають сценарій явно.
- **Inline guard:** якщо тіло if тільки ранній вихід (return, continue, break) та умова поміщається в один рядок — один рядок без фігурних дужок; інакше багаторядковий блок.
- **ESLint та lint-правила** проєкту — дотримуватися (npm run lint / аналог).
- **Більше 3 if за одним значенням:** switch (але не більше 10 case; далі — Map).
- **Map / Set:** коли потрібен частий lookup або унікальність, не скрізь.
- **Віддавати перевагу map, filter, reduce** замість ручних циклів, де читається краще.

## TypeScript

- **any заборонений** — unknown + явне звуження.
- **Публічні функції** — явний повертаємий type.
- **Тільки named export;** default export заборонений.
- **Форми об'єктів та контракти** — тільки через type. **interface заборонений у новому коді.**
- **Критично:** похідні type — тільки один шар одного utility від базового type: Partial, Required, Readonly, Pick або Omit.
- **Критично заборонено:** ланцюжки utility, кілька utility на одному type, Record, Exclude, Extract, Awaited, ReturnType, conditional types, mapped types, template literal types, перетин та об'єднання для збірки object type, сторонні type-хелпери. Union примітивів та string literal union (status, action) — дозволені.
- Від одного базового type — не більше 5 похідних через дозволені utility. Більше — розбити базовий type або використати іменований проміжний type (теж один utility від своєї бази).
- **Комбінація полів:** явний type або кілька іменованих type, не вкладені utility.

## Організація

- **Константи:** за доменами/зонами; без магічних рядків у коді (ключі i18n та доменні константи — у constants / locales).
- **Імпорти:** зовнішні пакети, потім types, потім локальні модулі; порожня лінія між групами; alias та ESM-суфікси — за конвенцією репозиторію.
- **async/await,** не .then-ланцюжки.
- **catch не порожній** — помилки не ковтаємо; логувати або прокидати з контекстом.
- **console.log:** тільки у розробці; на production-шляхах — логгер фреймворку.

## Тести

- **Критично обов'язково:** security / auth.
- При зміні нетривіальної логіки (розбір, нормалізація, агрегації, публічний API) — тести в тому ж PR.
- Інакше — за запитом або якщо поведінка неочевидна з коду.

---

## Стек та оточення

- Визначати стек за репозиторієм (package.json, pyproject.toml, Cargo.toml тощо) — не вгадувати фреймворк.
- Для web/mobile UI — safe-area, зони натиску, клавіатура — якщо проєкт це припускає.
- Новий npm-скрипт у завданні — один рядок у README в тому ж PR. Окремі .md-файли — тільки за запитом користувача.

---

## Git та поставка

- **Коміти:** тільки за явною просьбою користувача; повідомлення про те, навіщо, не список файлів.
- Без секретів у комітах; попередити, якщо у staging потрапив .env або ключі.
- **PR:** невеликі; test plan — якщо змінилася логіка з розділу Тести.

## Поведінка AI-асистента (коли застосовується)

- Чистий підтримуваний код, не одноразові хаки.
- Перед крупною фічею — коротко структура модулів.
- Виконувати команди самому: install, build, lint, test.
- Не здаватися після першої помилки.
- Відповіді за обсягом завдання: коротко / докладно.
